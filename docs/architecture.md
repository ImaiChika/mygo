# mygo 后端基础架构说明

## 1. 当前阶段的总体思路

`mygo` 当前采用“模块化单体（Modular Monolith）”作为第一阶段架构，而不是一开始就拆成多个微服务。原因如下：

- 实时聊天产品的早期复杂度主要来自业务一致性、消息投递、在线连接管理，而不是服务数量
- 模块化单体更适合快速演进，同时保留未来拆分能力
- 对于 Vue 前端尚未开始的阶段，先把后端边界打清楚，能显著降低后续前后端联调成本

## 2. 技术选型

### 2.1 Go + chi

- Go 非常适合高并发网络服务
- `chi` 基于标准库 `net/http`，风格轻量，适合长期维护
- 相比更重的框架，它更适合作为成熟项目的可控基础层

### 2.2 PostgreSQL

- 用于保存会话、成员关系、消息、协作房间元数据
- 对 JSONB、事务、一致性支持较好
- 适合聊天系统后续增加检索、扩展字段、审计记录

### 2.3 Redis

- 第一阶段主要用于跨实例实时广播
- 后续可以扩展到在线状态、限流、短期会话缓存、延迟任务
- 当前代码优先采用 Pub/Sub，后续可在异步任务场景接 Redis Streams

### 2.4 WebSocket

- 聊天消息、在线状态、输入中提示等低延迟双向通信采用 WebSocket
- HTTP API 负责管理型操作，WebSocket 负责实时事件投递

### 2.5 Yjs 预留而不是现在直接硬接

- Yjs 更适合富文本、白板、协作文档等 CRDT 场景
- 由于 Yjs 生态常与 `y-websocket` / `y-redis` 配合使用，当前版本在 Go 后端中先保留协作票据与房间元数据能力
- 后续如果进入协作编辑阶段，建议把 Yjs Provider 作为独立协作网关接入，而不是强行把 CRDT 同步逻辑塞进聊天服务

### 2.6 Consul 的使用建议

- 当前阶段不建议直接引入 Consul
- 原因不是它不好，而是目前还是单体后端基础建设阶段，服务发现与配置中心的收益还不够高
- 当前通过接口预留 `ServiceRegistry` 扩展位，等后续拆分为网关、聊天、协作、通知等服务时，再接 Consul 或直接使用 Kubernetes Service

## 3. 模块划分

### 3.1 system

- 健康检查
- 就绪检查
- 基础运行状态查询

### 3.2 chat

- 会话创建
- 成员管理
- 消息发送
- 历史消息读取
- 会话已读状态
- 实时广播事件生产

### 3.3 user

- 用户注册
- JWT 登录
- 当前登录用户资料

### 3.4 attachment

- 会话附件上传
- 附件元数据持久化
- 本地文件存储抽象

### 3.5 collab

- 协作房间元数据
- 协作访问票据
- 为未来 Yjs 服务提供授权与房间绑定能力

### 3.6 realtime

- WebSocket 连接管理
- 会话订阅关系
- 向单会话或多用户推送事件
- 对接 Redis Pub/Sub 做跨实例扇出

## 4. 当前代码中的扩展位

- `internal/platform/eventing`：本地事件总线与 Redis 事件总线
- `internal/platform/registry`：服务注册抽象，当前为 Noop
- `internal/platform/storage`：本地存储抽象，后续可替换为对象存储
- `internal/modules/collab`：预留 Yjs/协作文档接入点
- `internal/platform/auth`：JWT 签发、解析与鉴权中间件

## 5. 未来演进路径

### 5.1 第二阶段

- 引入正式登录体系（JWT / Refresh Token）
- 增加用户、组织、群组、权限模型
- 补全消息撤回、已读回执、未读数

### 5.2 第三阶段

- 增加消息投递保障与异步任务
- 支持对象存储上传附件
- 加入全文检索与审计能力

### 5.3 第四阶段

- 独立协作编辑网关
- Yjs Provider + Redis / Kafka 扩展
- 多租户与多地域部署
